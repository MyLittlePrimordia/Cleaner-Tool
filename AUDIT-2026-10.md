# Cleaner Tool — Deep Audit

**Date:** 2026-10-21 · **Scope:** whole repo (79,431 LOC in `app/`, 4,488 LOC tests) · **Target:** Windows 10/11, Python 3.10+, stdlib-only runtime, PyInstaller one-file build

**Method:** full read of the high-risk modules (`ui/app.py`, `ui/widgets/chrome.py`, `ui/tabs/*`, `runner/`, `utils.py`, `tasks/clean_tasks.py`, `tasks/install_tasks.py`, `self_update.py`, `elevation.py`), 331-test suite, `pyflakes`, instrumented startup and tab-switch timing against the real Tk app, geometry inspection of the custom chrome, WCAG contrast maths on the palette, and web research on current Windows-cleaning practice, Material 3/Tk constraints and the 2025–26 competitor landscape.

All timings below were measured on this machine from source (warm OS cache, 100% DPI); the packaged `.exe` adds PyInstaller extraction time on top.

---

## 0. Verdict

This is **not** a typical hobby Tk app. The safety work (reparse-point guards, protected-root list, quarantine, snapshot/revert, SHA-256-verified updates, honest run results) is better than most commercial cleaners, and the 331-test suite plus the SEC-001 allowlist guard are real assets.

The problems are concentrated in three places:

1. **One P0 functional regression** — the "save my selection" path is dead, so scheduled Auto Maintenance has nothing to run on a fresh install.
2. **A custom-chrome bug** — the rounded-corner masks are painted *over* the close button (confirmed 8×10 px overlap), which is exactly the "square over the exit button" artifact.
3. **Performance work that is self-inflicted** — ~95% of tab-switch time is two synchronous `update_idletasks()` calls; removing them measured **10–20× faster switching**.

Everything else is hardening, polish, and a strong feature roadmap.

## 2. Bugs in detail

### B1 — P0: saved selection is never persisted

`run_tasks()` computes:

```python
# ui/app.py:4194
all_selected = list(tasks)  # H1: capture real selection before filtering
```

and then calls `self._start_claimed_run(gen, tab_name, tasks, mode, quiet, toast_kind, toast_extra)` — **without `all_selected`**. Inside `_start_claimed_run`, the save block is:

```python
# ui/app.py:4305-4312
try:
    from app.config_persist import update_config as _update
    def _mut(cfg, tab_name=tab_name, all_selected=all_selected):   # <- global lookup
        cfg.setdefault("selected_tasks", {})[tab_name] = [t.key for t in all_selected]
    _update(_mut)
except Exception:
    pass          # <- NameError dies here
```

`all_selected` is not a parameter, not a local, and not a global. `pyflakes` flags it; `dis` shows `LOAD_GLOBAL all_selected`. The exception is swallowed, so the run appears normal.

**Impact.** `DEFAULT_CONFIG["selected_tasks"]` is `{"Clean": [], "Repair": [], "Tweak": []}` (`config_persist.py:62-66`) and this is the only writer of that key in the whole app (`grep selected_tasks`). Consequences:

* Auto Maintenance (Settings, described as "Runs your last selected tasks on a schedule") calls `run_auto_clean(selected)` (`__main__.py`), which returns `(False, "No tasks selected for auto-clean")` (`scheduler.py:562-563`). **On a fresh profile, the scheduled clean silently does nothing.**
* Existing profiles keep whatever an older build last wrote — i.e. a stale task list, which is worse than none because it will run untended.
* The Tweak/Auto-Pilot path deliberately doesn't write it (`quiet=True`), so nothing else repairs it.

**Fix.** Add `all_selected` to `_start_claimed_run`'s signature and pass it from `run_tasks`; use `all_selected` (not the admin-filtered `tasks`) in the `_mut` closure, as the comment intends. Then add a regression test that drives `run_tasks` with a stub task and asserts `selected_tasks["Clean"]` contains its key. This is a 4-line fix plus a test.

### B2 — P1: the corner mask is painted over the ✕ button

The borderless window uses `-transparentcolor` plus four 18×18 canvases ("corner masks"). `_layout_grips()` lifts the masks last, above the title bar (`chrome.py:404-410`), and each mask paints an opaque disc of `COLORS["shell"]` inside a canvas whose background is the transparent key.

Measured geometry at 1280×747:

```
close button   x 1233..1272   y 6..34
NE mask canvas x 1264..1282   y -2..16
overlap        8 px wide × 10 px tall
```

So the **top-right 8×10 px of the close button is covered by an opaque shell-coloured fillet**. At rest it is invisible (button background is also shell), so nobody notices; on hover the button turns red and a dark square/notch appears over its corner — the reported artifact. Because the mask canvas is above the label, that same 8×10 px is also a **dead click zone** on the ✕ (clicks hit the canvas, which has no binding).

The maximize button is 4 px clear; only ✕ overlaps today, but a wider glyph, a different font, or `RADIUS` becoming 20 re-creates it for all three.

**Fixes, in order of preference:**

1. **Keep controls out of the corner arc.** Pack the buttons with a right inset ≥ `RADIUS + 4` (e.g. `close.pack(side="right", padx=(0, 20), pady=6)`), or raise `TITLE_H` and inset vertically. This is a one-line change and keeps the current design.
2. **Draw the fillet only where nothing interactive lives** — e.g. give the title bar exclusive ownership of the top 16 px and make the masks 8 px, but this fights the layout.
3. **Drop the masks on Windows 11** and ask DWM for `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND` (attribute 33). Microsoft documents that DWM *cannot* round a window that uses per-pixel alpha or window regions; Tk's `-transparentcolor` is color-key layering rather than per-pixel alpha, but it is still a custom-shaped layered surface, so this must be validated on a real Win11 build rather than assumed. Practically, expect to drop `-transparentcolor` (and accept square corners on Windows 10). If it works, it is the only route to properly **antialiased** corners; the current `create_oval` masks are hard-edged at every DPI.

**Add a guard test** that asserts, for every title-bar button rect, no intersection with any chrome overlay (`_corners`, `_grip_widgets`). That turns "someone moved a button" into a failing test instead of a screenshot bug.

Related polish: `_layout_corners()` leaves an unused `C` local (`chrome.py:194`), and the masks are not re-laid-out for `maximized` (a maximized window still gets rounded mask corners, which looks wrong against the screen edge).

### B3 — P1: tab switching is 10–20× slower than it needs to be

`_switch_to()` calls `_show_tab()` (which flushes at `app.py:1752`) and then flushes **again** at `app.py:1596`:

```python
self._show_tab(name)
self.root.update_idletasks()
self._tick_switch()
```

Measured, with every page already built and mapped:

| Switch | Now | With `update_idletasks` suppressed | Flush share |
|---|---|---|---|
| Repair | 42.2 ms | 3.9 ms | 40.4 ms (96%) |
| Tweak | ~30 ms | 5.1 ms | — |
| Install | 12.7 ms | 7.0 ms | 3.8 ms |
| Tools | 89.0 ms | 6.7 ms | 87.3 ms (98%) |
| Drivers | 45.5 ms | 3.9 ms | 44.0 ms |
| Settings | 42.8 ms | 3.5 ms | 40.2 ms |
| Clean | 7.6 ms | 3.6 ms | 3.3 ms |

The pages are all stacked with `place()` and switched with `tkraise()` — a raise needs **no layout pass at all**. The flushes force Tk to reconsider every hidden page in the stack on every click. That is the "I can watch the content render" stutter; the rail animation also starts after the freeze, so its first frames are skipped and the indicator appears to jump.

**Fix:** delete both calls (or move the first-map flush to `after_idle`, conditioned on `_first_map`). The page appears one event-loop turn later (~16 ms), the click is acknowledged immediately, and the 200 ms indicator animation gets its full frame budget. Keep the `update_idletasks()` inside `_premap_install` (`app.py:1318`) — that one runs off the click path and is doing real work.

### B5 / B6 — two more `NameError`s

* `installtab.py:1448`: `_open_url` is a `@classmethod`, but the last-resort error dialog calls `_themed_showerror(self, ...)`. If all three open routes fail (LTSC with no browser association is the documented case), the handler raises `NameError` instead of showing the error — reintroducing the "links do nothing" bug it was written to fix. Make it an instance method (`def _open_url(self, url)`) or pass the toplevel explicitly.
* `tasktab.py:406`: the Game Session pill's fallback is `_ICON_FALLBACK["gamesession"]` (bare name) instead of `self._ICON_FALLBACK[...]`. If `preset_icons/gamesession.png` is missing or fails to decode, **the entire Tweak tab construction raises** — a packaging miss turns into an unusable tab instead of a graceful fallback. (The comment directly above claims it degrades gracefully.)

Both are caught by `pyflakes` today. See B13.

### B7 / B8 — install-tab startup work

`InstallTab.__init__` immediately starts two worker threads:

* `_start_installed_badge_scan()` → `get_installed_ids()` → `winget export` (**0.68 s** measured) **plus `winget list` (0.59 s)** **plus** `Get-AppxPackage` via PowerShell (~1–2 s), and
* `_start_update_count_scan()` → `winget upgrade` (seconds), and
* `capabilities.has_winget()` shells out to `where.exe winget` (**0.13 s**).

That is **four heavy subprocesses at every launch**, for a tab the user may never open. Worse:

* `get_installed_ids` runs `winget list` **even when `winget export` already succeeded** (`install_tasks.py:1704-1712`); the list is only needed as a fallback and for Store name hints — and those hints are already superseded by the exact `Get-AppxPackage` check.
* There is no lock or single-flight wrapper around `winget`, so the export/list/upgrade calls can overlap. winget has an internal installer mutex and concurrent calls are a known source of hangs/"another instance" errors. `_UPGRADE_CACHE`/`_INSTALLED_CACHE` are bare lists with no lock.
* `_run_winget` returns `stdout` **without checking `returncode`** (`install_tasks.py:1590-1605`), so a failed command's error text is fed to the parsers (the parsers mostly defend themselves, but the fallback token matcher can invent badges from error text).
* `--include-versions` on `winget export` is not needed (only `PackageIdentifier` is read); it made the export slightly slower in measurement (678 ms vs 664–694 ms, within noise) and doubles the file size.

**Fix:** make the Install scans lazy (first visit) and single-flight; cache to disk with a TTL; skip `winget list` when export parsed; check `returncode`; centralize winget calls in one module with a `threading.Lock` and `--disable-interactivity` everywhere.

`_show_tab("Install")` also calls `_start_catalog_build()` (`app.py:1728`), which executes one catalog slice **synchronously inside the click**. On a cold catalog that is the 433 ms first-visit case measured. Schedule it with `after(0)` instead.

## 3. Performance

### Measured

| Phase | Time | Note |
|---|---|---|
| `import app.ui.app` | 140–150 ms | (`-X importtime` inflates this to 785 ms — don't quote that) |
| `Application()` build | 474–502 ms first, 291 ms second | ~400 widgets; widget creation itself is only ~14 ms |
| ├ `SettingsTab` ctor | ~180 ms | 85–94 ms of it is `schtasks /Query` × 3 |
| └ remaining inline build | ~110–180 ms | status row, panel, log, drive chips |
| Gate visible → full UI | ~0.5 s extra | no progress indicator while it happens |
| Process start → gate visible | 0.55 s | source, warm cache |
| Tab switch | 42–89 ms | 96–100% layout flush (B3) |
| Install tab, catalog cold | 433 ms | slice built in the click path (B8) |
| `winget export` / `list` / `where` | 0.68 s / 0.59 s / 0.13 s | all at startup |
| `settings_apply.resync_flags()` | 85–244 ms | 3 `schtasks` calls, on the UI thread |

### Highest-ROI fixes

1. **B3 flush removal** — 30–80 ms off every tab click, one-line change, no visual downside.
2. **Lazy `SettingsTab`** — not the default tab, but always built. Constructing it on first visit removes ~180 ms from the post-gate build and defers three `schtasks` calls. Same argument, smaller win, for `ToolsTab` (~96 ms).
3. **Defer `settings_apply.resync_flags()` to a worker** after first paint. It is a pure status probe; blocking the UI for 90–240 ms at startup to label a toggle is a bad trade.
4. **Lazy Install scans + single-flight winget** — removes four subprocesses from every launch.
5. **`after(0)` the first catalog slice** — removes the 433 ms cold-click case.
6. **Move `_premap_install` to the front of the idle chain** (it currently runs after four body prewarms) and add a hover prewarm on the Install rail item.
7. **Skip `winget list` when export worked** — ~0.6 s and one process.
8. **Single-instance poll** — move to a blocking worker thread + dispatcher post (or 2 s interval); no functional change, fewer wakeups on battery.
9. **Packaging** — PyInstaller `--onefile` extracts the interpreter + stdlib to `%TEMP%` on every launch (PyInstaller documents one-file as slower to start). If cold-start complaints persist, ship `--onedir` in a zip (or keep one-file and add a splash). Measure both; don't guess.

### Startup architecture note

The gate → main-UI transition is a single monolithic build with no feedback. If you keep it, at minimum set a status ("Setting up…") and flush once before the build so the user sees it. Better: build Settings/Tools/Drivers lazily and chunk the rest, as `InstallTab` already does.

## 4. Hardening & refactor

### Do these first

* **Put `pyflakes` (or `ruff`) in CI.** All three undefined-name bugs would have failed the build before release. It is a 3-line workflow addition and zero runtime cost. The codebase is otherwise clean — only 4 non-cosmetic lint findings, all listed here.
* **Add a crash log.** There is no `sys.excepthook`, `threading.excepthook`, or `Tk.report_callback_exception` handler. In the windowed `.exe`, an unhandled Tk callback exception goes to a nonexistent stderr and vanishes. Install all three at startup, write to a rotating file under `%LOCALAPPDATA%`, and add **Settings → "Copy diagnostics"** (version, OS build, last N log lines). This is the single highest-value support feature you can add.
* **Audit the `except Exception: pass` policy.** 2,309 broad handlers, 1,344 silent. Most are legitimate best-effort UI guards, but they are also why B1 survived. Adopt: *if the handler is on a state-changing path, log at least once* (you already have `log_or_swallow` — use it consistently). Keep `pass` only for cosmetic/teardown races.
* **Supply chain:** the build workflow has workflow-level `contents: write`, runs on every push to `main`, and publishes/overwrites the rolling `latest` release that every installed app auto-updates from. Pin actions by commit SHA, scope `permissions` to the job, set `persist-credentials: false`, and gate the auto-update channel to a `stable` tag (or at least require the test suite + a smoke run before the release step). An unsigned build is also the main SmartScreen/Defender friction point — code signing is the highest-leverage remaining distribution fix (the workflow already has the hook).

### Refactor targets, in order

1. **`app/ui/app.py` (5,026 lines)** — the composition root also owns run lifecycle, tray, dialogs, chrome glue, disk chips, nudges and update UI. Extract: `RunController` (claim/preflight/worker/scorecard), `StatusRow` (mode/health/drives/nudge), `TrayController`. The file's own comments show the seams.
2. **`app/tasks/tweak_tasks.py` (5,833 lines)** — split by domain (system, network, GPU, privacy) with one registry import. Keep `TASKS` assembled in one module so SEC-001's drift guard still sees literals.
3. **`app/gui.py` wildcard facade** — replace `from app.ui.dialogs import *` with explicit re-exports. Wildcards make `pyflakes` give up on the module and hide exactly the class of bug above.
4. **`app/tasks/install_tasks.py`** — split winget plumbing (one `Winget` class, lock, rc-checked run, parse) from the download/install tasks. This is where B7 lives.
5. **Typed outcomes** — the `TaskOutcome` work in `runner/` is good; extend it to return a structured "what changed" record so the scorecard can diff before/after instead of re-measuring.

### Test gaps to close

* saved selection persistence (B1) — would have caught P0;
* chrome geometry invariants (B2);
* a smoke test for every tab's first and second show under a time budget (B3) — e.g. assert `< 25 ms` warm on this class of machine; CI machines are noisy, so assert on a generous ceiling;
* install-tab scan single-flight and "no winget at startup" (B7);
* one end-to-end elevated run path (currently everything is faked at the runner boundary);
* `pyflakes` as a gate (B13).

## 5. Task-safety review (your data-loss surface)

The guards themselves are strong: protected-root refusal, reparse-point pruning at every level, re-check immediately before delete, quarantine support, dry-run honored by pure tasks, cancellation polled per file, honest partial totals. What needs product decisions is the **default selection and the risk taxonomy**. The labels barely discriminate: 53 of 57 Clean tasks are `SAFE` (the other 4 are `ADVANCED`), and the two data-loss tasks below are among the `SAFE` ones.

### Defaults that should change

| Task | Problem | Recommendation |
|---|---|---|
| `recycle_bin` in **Quick Clean** | The Recycle Bin is user data and the only undo for "oops, deleted". Emptying it on a 1-click preset is irreversible. | Default **off** in Quick Clean; keep in Deep Clean, or make it opt-in with a count/size preview ("1,284 items, 3.2 GB") like Storage Sense. |
| `driver_junk` in **Quick Clean** | Despite the label "Remove Old Drivers", it deletes extracted installer packages (`C:\NVIDIA`, `C:\AMD`, `C:\ATI`, `C:\Intel\Driver`) when no `.sys/.dll/.inf` is found. Those packages are what let a user reinstall a driver offline; vendors and DDU guidance treat them as useful. | Rename to "Driver Installer Leftovers", default **off**, prefer **Quarantine** (you already have it), never delete the newest package. |
| `shader_cache` in **Quick Clean** | Safe to delete, but games recompile and stutter on next launch, and clearing caches does not raise FPS. Research is consistent on this. | Keep, but label "may cause brief stutter on next launch"; skip caches for **running** games; consider an age filter. |
| `thumbnail_cache` (default-on, Deep Clean) | Force-kills Explorer mid-run with no warning; every open Explorer window and the taskbar disappear. | Ask first ("Restart Explorer to clear locked thumbnails?"), or skip locked `.db` files and leave the shell alone. |
| `old_logs` (Quick Clean) | Deletes CBS/DISM/WindowsUpdate logs — the evidence needed to diagnose a failed update or servicing operation. | Keep out of Quick Clean; call it "Diagnostic Logs (troubleshooting evidence)". |
| `remove_bloat` (Deep Clean) | Uninstalls preinstalled apps. It is honest about being irreversible, but "Deep Clean" reads like file cleanup. | Separate confirmation listing the apps, and require an explicit checkbox. |

### Safety features worth adding

* **Running-game/launcher guard.** Before cleaning shader/launcher/engine caches, enumerate running processes (`tasklist` or `EnumProcesses`) and skip caches belonging to a running game/launcher, with a log line. Deleting a shader cache under a live game is the one realistic way this app can cause a crash or a bad match.
* **Risk taxonomy instead of one label.** `SAFE` / `REVERSIBLE` (snapshot) / `NEEDS REBOOT` / `DATA LOSS` / `IRREVERSIBLE`, each with its own confirmation. Right now 53 of 57 Clean tasks read `SAFE`, including Recycle Bin and driver leftovers, which trains users to ignore the badge.
* **Preview before destructive tasks.** You already run every task in dry-run for Storage Insight; reuse that to show "1,284 files, 3.2 GB — includes 14 items modified in the last 24h". A single "recently modified" count would prevent most accidental data loss.
* **Quarantine by default for anything not regenerable**, not just opt-in.

Research cross-check (sources at the end): Recycle Bin, driver packages and diagnostic logs are the three places where "cleaner" defaults most often destroy something a user needed. Prefetch/SysMain disabling is correctly *not* in the presets — keep it that way.

## 6. Design audit (Material 3 in Tk)

### What is genuinely M3-correct

* **Color roles**: an actual role palette with containers, on-colors and state layers; contrast is excellent (text 14.5:1, subtext 10.9:1, muted 5.8:1, black on accents 9.1–11.8:1 — all above WCAG AA, most AAA).
* **Shape scale** (`SHAPE_XS…XL`), **type scale** (`TYPE`), **state-layer opacities** (8/10/16%) are centralized and used.
* **Navigation rail** dimensions match M3 closely (88 px rail, 56×32 indicator, 24–36 px icons, label below).
* Buttons are canvas-drawn with hover/press/focus/disabled states and real keyboard activation — better than most Tk apps.

### Problems that read as "not designed"

1. **The corner artifact (B2)** — highest priority; it is on the most-used control in the window.
2. **Aliased window corners.** The masks are `create_oval` on a color-key canvas: no antialiasing. At 100% it reads as a slightly chunky 16 px radius; at 125/150% it is visibly jagged. This is inherent to the mask technique, not a Tk limitation you can style away.
3. **Icon language is split in two.** Preset cards, nav rail and status row use monochrome generated PNGs; the Tools grid still uses full-color emoji (💾 🗑️ 📊 🎮 …). Emoji are rendered by the system font, so they ignore the palette, vary between Windows builds, and are the loudest thing on an otherwise restrained page. Generate the same monochrome set for the 24 tool cards (you already have the pipeline).
4. **No focus path through the main content.** `AnimatedButton` is focusable; the nav rail canvas is focusable but `Return`/`Space` are bound to `None` (`app.py:1437-1438`), and preset cards are `Frame`s with click bindings — not reachable by Tab. A keyboard user can switch tabs with Ctrl+1..7 but cannot choose a preset or open a tool card. Add `takefocus` + `Return`/`Space` to cards, and make the rail activate on Enter.
5. **All motion, always.** Hover easing on every card, 16 ms tickers, rail animation, no reduced-motion setting. Add a Settings toggle that skips animations (also helps remote-desktop/VMs where every timer repaint is expensive).
6. **High-DPI icons.** Fonts scale with DPI; `PhotoImage` icons are fixed pixels and are only resized by integer `subsample()`. At 150% the 24/36 px icons stay physically small next to scaled text, and at 125% `subsample` cannot hit the target at all. Ship @1x/@2x assets and pick based on `winfo_fpixels("1i")`.
7. **Tooltip noise.** Preset cards create one Tooltip per card part (7 widgets) carrying the same sentence that is already visible as the card blurb. Tooltips should appear only when content is ellipsized; otherwise every hover shows a duplicate label.
8. **The "1-click" promise costs two clicks.** On launch `mode="preset"` and `_selected_preset=None`, so `selected_tasks()` is empty, Run is disabled, and the user must click **Quick Clean**, then **Run**. Preselect Quick Clean (or restore the last preset) so the primary CTA is live on first paint. This is the single best UX change in the app.
9. **Status row density.** Privilege, PC health, update chip, three hidden corner icons, drive chips, nudge chips and Stop can all coexist in one strip; at the 980 px minimum width they compete with the status text. Consider moving drive chips into a popover/menu (one "C: 42 GB · D: 120 GB" chip) and keeping only run-state + health inline.
10. **Settings nav item is grey** (`TAB_ACCENTS["Settings"] = subtext`), which reads as disabled rather than neutral. Use `on_surface_variant` or an outline icon in `text` colour.
11. **Fixed-size dialogs.** Every popup is the same footprint; that is good for rhythm, but on a 1366×768 laptop some content scrolls that would fit on a taller window. Your fit tests cover clipping; consider clamping height to the work area and letting the card grow to content within min/max.

### Should you leave Tk?

Not yet. The problems above are ~90% fixable in Tk, and the zero-dependency + one-file distribution is a real product advantage (a Qt/Flet/Tauri migration adds 40–150 MB, a toolchain, and a new class of packaging bugs). The honest boundary: if you want per-pixel antialiased rounded windows, real shadows/elevation, smooth 60 fps compositing, accessible native controls, or a light theme at high fidelity, Tk will keep costing you. A pragmatic path is to keep Tk for this release cycle, fix the perf/chrome issues, and prototype the *shell* (window + rail + page container) in PySide6 or a WebView2/Tauri front-end before committing to a rewrite. Do not mix toolkits incrementally.

## 7. Feature roadmap

Ordered by value-to-effort, filtered against what already exists (you already have: restore points, tweak snapshots/undo, quarantine, driver updates, save-game *backup*, speed/DNS/server-ping tests, hardware monitor, startup manager, storage insight, duplicates, process manager, services, file-lock finder, install profiles, run history, Auto-Pilot).

### Tier 1 — high value, small/medium effort

1. **Game Save Manager (restore, not just backup).** `backup_game_saves` already zips Saved Games / My Games / Minecraft and prunes to 5. Add a Tools card that lists backups, shows contents, restores to a chosen folder (never overwriting silently), verifies the archive, and warns when Steam Cloud is enabled. Research consistently ranks save backup/restore among the most valued gamer utilities.
2. **"Is a game running?" guard** (see §5). Cheap, prevents the only realistic crash path.
3. **Startup impact column.** Startup Manager can show publisher/signature, source (Run key vs Startup folder vs scheduled task vs service), and an estimated impact band using Microsoft's documented CPU/disk thresholds. It turns a list into a decision.
4. **Missing-runtime detector.** Install tab already installs VC++/DirectX/.NET/Java. Add a read-only scan that reports which VC++ 2015–2022 x86/x64 runtimes and DirectX components are present, then offers only the missing ones. This is what "game won't launch" usually needs.
5. **Game Readiness card** (Tools). One screen: Game Mode, Game DVR, power plan, GPU driver age, refresh rate, HDR/VRR support, free space on the game drive, and pending reboot — each with a one-click fix that routes through the existing tweak engine and its undo.
6. **"Last clean" summary on the Clean tab.** You already record history; surface "Last run: 3 days ago · 4.2 GB · 2 skipped" above the preset cards. It makes the 1-click button feel alive.
7. **Repair log digest.** When SFC/DISM finishes, parse `CBS.log`/DISM output for the first real error and show a plain-English line ("component store repaired 3 files; 1 could not be fixed — run Deep Repair"). You already collapse progress spam; this is the natural next step.
8. **Bufferbloat / latency-under-load** in the Speed Test. Measure ping while saturating the link; gamers care more about that than peak Mbps, and it differentiates you from every "speed test" clone.

### Tier 2 — bigger bets

9. **Per-game storage & shader-cache inventory.** Scan launcher manifests (Steam `libraryfolders.vdf`, Epic manifests) and show per-game install size + cache size + last played, with a "safe to delete" preview. Extends Storage Insight from "disk" to "games".
10. **Driver clean-install handoff.** Detect GPU vendor and driver version, offer a restore point, then guide the user through DDU/AMD/NVIDIA's own clean-install flow (open the official page, detect Safe Mode). Do **not** implement driver-store deletion yourself — that is how apps brick machines.
11. **Windows upgrade cleanup with explicit rollback warning.** You have `update_leftovers`; add a first-class card showing Windows.old size, the 10-day rollback window, and an irreversible-action confirmation. Microsoft's own Storage UI does this; matching its wording builds trust.
12. **Downloads/installer cleanup with age + preview.** "Installers older than 30 days in Downloads" is one of the largest safe wins on gamer PCs, and nobody in your preset list covers it.
13. **Portable mode.** Config/logs beside the exe when a `portable.flag` exists. Fits the "zero install" positioning and USB-stick use.
14. **Scheduled-maintenance dashboard.** Next run time, exact task list, last result, and a "Run now" button — this also gives B1 a visible regression test in the UI.
15. **Light theme + reduced motion.** The palette is role-based already; a second palette plus the motion toggle is mostly data, and it addresses accessibility and daytime use.

### Tier 3 — differentiators / long bets

16. **Per-game Auto-Pilot profiles.** Auto-Pilot already applies a Tweak preset per session; extend to per-game profiles (e.g. competitive shooters get latency tweaks, cinematic games don't) with an explicit, reviewable diff.
17. **Local-only diagnostics bundle** (`Settings → Export support bundle`): version, OS build, last run log, config (redacted), driver list. No telemetry — privacy is a selling point; make support easy without it.
18. **Signed task packs / plugin SDK.** A manifest format for community clean/repair tasks, signature-checked, with the same safety primitives. High ceiling, high review burden; only after the core is stable.
19. **Localization.** All copy is inline English. M3 layouts with 30% expansion need testing; German/Portuguese/Brazilian Portuguese are the obvious gamer markets.
20. **Shell rewrite evaluation** (PySide6/WebView2) — prototype only, per §6.

### Explicitly do *not* add

Registry cleaning, RAM "boosters"/standby-list purging on a timer, HPET/timer-resolution presets, pagefile disabling, TCP "optimizer" bundles, or service-disabling presets sold as FPS gains. Research and Microsoft's own docs are consistent: no reliable universal gain, real regression risk, and they would undercut the trust the rest of the app has earned. (SysMain disabling already exists as a custom-only task — keep it custom, and consider adding a "varies by system" note.)
